# 可行性评估

评估对象：**Durable Agent Runtime** —— 可崩溃恢复、可确定性重放的 Agent 运行时，日志是事实来源，语义记忆（HNSW）是派生索引。

## 一、结论

**可行，而且这个组合在逻辑上是自洽的。** 前提是采用"日志为真相、索引为派生视图"的拓扑；如果改成写路径同步更新索引，或者把索引当成第二个事实来源，就会变成硬塞。

时间放宽后（业余长期），原先"8 周做不完"的反对理由消失；剩下的风险是范围控制，不是可行性。

| 维度 | 判断 | 说明 |
| --- | --- | --- |
| 逻辑自洽 | 高 | 生产者/消费者关系，标准的事件溯源 + 物化视图 |
| 技术可行性 | 高 | 单机、无外部服务依赖；所需技术都有成熟参考 |
| 学习密度 | 很高 | WAL、崩溃一致性、重放、幂等、事件溯源、ANN |
| 面试信号 | 很高 | 可追问两小时，且有可验证数据 |
| 范围风险 | 中高 | 两个硬组件；靠分期和降级控制 |

## 二、为什么这个组合不是硬塞

### 成立的关系

- **Journal 是事实来源**：Agent 的每一步都追加到日志，崩溃后重放恢复。
- **索引是派生视图**：indexer 异步消费日志，把 episode 投影进 HNSW；索引可以落后、可以重建。
- **写路径单向**：引擎不等索引；索引故障不影响 run 的持久性。
- **读路径显式**：`memory.search` 是普通 activity，有超时/重试；索引挂了只影响这一步。

这和"数据库 → 搜索索引"是同一个模式：主存储负责真相，搜索引擎负责查询，索引可以从主存储重建。两者有真实的**数据流**，不是靠一个 trait 硬拼。

### 不成立的关系

| 方案 | 为什么不成立 |
| --- | --- |
| 写路径同步更新索引 | 索引延迟进入关键路径；索引故障导致 run 失败；日志和索引出现部分写入 |
| 索引作为第二个事实来源 | 两份真相会分叉；恢复时不知道该信谁 |
| 把索引 upsert 全部写进 journal，靠重放重建 | 语义上可行，但索引变更量大、重放慢；索引需要自己的快照/并发读，和工作流状态机不是一类东西 |
| 同一 repo 但两个互不调用的模块 | 那是 monorepo，不构成一个项目 |

## 三、这个项目的硬问题

这些问题决定了它不是一个"拉模型 + 存向量"的 Demo：

1. **崩溃一致性**：进程在任意写入边界崩溃，恢复后状态必须可解释。
2. **至少一次语义**：活动可能重复执行；外部副作用靠幂等键收敛，不能假装 exactly-once。
3. **重放确定性**：同一日志重放必须得到相同状态；工作流里不能有隐藏的非确定性。
4. **checkpoint 原子性**：索引写完但 checkpoint 没落盘，重启后重放必须幂等。
5. **日志保留 vs 索引 offset**：日志截断后索引如何对齐/重建，是最容易埋雷的地方。
6. **新鲜度语义**：索引落后时查询返回什么，watermark 怎么定义。
7. **HNSW 的召回/延迟/内存权衡**：从零实现，并用暴力索引做基线。

## 四、与现有系统的关系

- 持久化执行：Temporal、DBOS、Restate 等已经证明这个方向有价值；本项目是单机、嵌入式、面向 Agent 的简化实现，不声称超越它们。
- 事件溯源 + 物化视图：Kafka → 搜索索引是成熟模式；本项目把 journal 和索引放在同一个进程/仓库里，便于学习和演示。
- HNSW：已有大量实现；本项目从零写是为了学习和可验证的召回/延迟数据，不是追求 SOTA。

面试叙事应该是："我实现了一个最小可验证版本，用数据验证了几个不变量"，而不是"我发明了一个新架构"。

## 五、风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 事件 schema 反复返工 | P1 延期 | P0 先定契约，写 ADR；只加字段不改语义 |
| 日志截断与索引 offset 冲突 | 数据不一致 | MVP 不截断；索引用稳定 episode id + episode store |
| HNSW 范围膨胀 | P3 拖延 | 只做单机内存 + 快照 + tombstone；不追分布式/GPU |
| 手写进度慢 | 总周期拉长 | 每阶段可停；P2 后用暴力索引也能交付 |
| 嵌入依赖 | 测试不可复现 | 测试用确定性 hash embedder；真实模型后置 |
| 把"至少一次"说成"exactly-once" | 面试扣分 | 文档、README、讲稿统一表述 |

## 六、数据与验证

项目成立与否，取决于能不能产出这些数字：

**Engine**

- 20 个崩溃点 × 100 次运行，不变量违反 = 0
- 恢复时间 vs 日志大小
- 吞吐：每条 fsync vs group commit
- 重放 100 次状态哈希一致

**Memory**

- recall@10（HNSW vs 暴力索引）
- 查询 p99、QPS、内存
- 索引落后 p50/p99、崩溃后追平时间
- 重复 episode 数 = 0
- 索引重建时间

**Integration**

- 写入到可检索延迟
- engine 崩溃 + indexer 崩溃组合下的恢复结果
- 快照/重建后召回率

## 七、最终建议

做。把 P0 的契约当成第一等公民；先让 P1 的崩溃恢复站住，再加记忆管线；HNSW 放最后，并且允许降级。这个项目比"安全网关"更难，但难在可验证的正确性，而不是"多接一个库"——这正是它作为面试项目的价值。
