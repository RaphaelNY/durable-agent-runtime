# 面试价值与叙事

这个项目的面试价值来自一句话：**日志是事实来源，索引是派生视图；崩溃后可恢复，重放可复现，索引可重建。** 所有的追问都围绕这句话展开。

## 一、哪些部分值钱

| 模块 | 信号 | 值钱的原因 |
| --- | --- | --- |
| Journal / 崩溃恢复 | 很高 | fsync、torn write、校验和、恢复边界 |
| 重放与确定性 | 很高 | 状态机、非确定性检测、状态哈希 |
| Activity 幂等 | 高 | 至少一次语义、幂等键、重复副作用 |
| checkpoint / 派生视图 | 很高 | 原子性、追平、重建、日志保留 |
| HNSW | 高 | 算法、召回/延迟/内存权衡、持久化、删除 |
| 背压与新鲜度 | 高 | lag、watermark、最终一致 |
| Embedder | 低 | 用确定性桩即可，不是重点 |
| CLI / UI | 低 | 面试不看 |

时间有限时，从 Journal、重放、checkpoint 往下做；HNSW 放最后，允许降级。

## 二、15 个必答追问

| 问题 | 回答要点 | 常见坑 |
| --- | --- | --- |
| 为什么日志是事实来源？ | 单一顺序、可重放、可审计、可派生索引；恢复和调试都靠它 | 说成"日志方便排查"不够，要讲恢复和派生 |
| 副作用已发生、日志没写，崩溃后怎么办？ | 无法自动消除；重新执行 + 幂等键；文档明确至少一次 | 声称 exactly-once 直接扣分 |
| 为什么不能 exactly-once？ | 外部副作用和本地日志没有共同事务；除非外部系统参与幂等/事务 | 要能举"扣款后崩溃"的例子 |
| 幂等键怎么设计？ | `hash(run_id, step_id)`，重试复用；外部系统按 key 去重 | 把 attempt 放进 key 会导致重试无法去重 |
| 活动重试会不会重复执行？ | 会；已完成的活动重放时复用结果，不重新执行；未记录的会重跑 | 混淆"重放复用"和"执行去重" |
| journal 尾部写坏了怎么办？ | 校验和/解析失败 → 截断到最后一条完整记录；告警 | 直接忽略坏行会掩盖数据丢失 |
| fsync 每条 vs group commit？ | 前者持久性好、吞吐低；后者有丢失窗口；用数据说话 | 只说"我们用了 fsync" |
| 重放怎么保证确定性？ | 工作流不能读时钟/随机/IO；命令序列必须匹配历史；状态哈希校验 | 把"重放"说成"再跑一遍" |
| 快照和日志怎么对齐？ | 快照带 offset + 校验和；恢复 = 快照 + 后续日志 | 快照和日志各存各的，没有 offset |
| 索引写完但 checkpoint 没落盘？ | 从旧 checkpoint 重放；upsert 幂等；重复数应为 0 | 假设 checkpoint 和索引同一事务 |
| 为什么索引不同步写？ | 故障隔离、延迟；写路径不能依赖检索 | 为了"实时"把索引放进写路径 |
| 索引落后时查询返回什么？ | 最终一致；返回 watermark；可选 wait | 声称强一致 |
| 日志截断后索引怎么办？ | 稳定 episode id + episode store；保留窗口；重建 | 用裸 offset 做长期 ID |
| HNSW 为什么不用 IVF/flat？ | 召回/延迟/内存的权衡；flat 是基线；参数 M/ef | 没有数据就说"HNSW 更好" |
| 删除怎么处理？ | tombstone + 周期性重建；观察召回率 | 直接物理删除导致图断裂 |

附加题：单写多读怎么加锁？indexer 落后怎么背压？schema 升级怎么兼容旧日志？

## 三、三个版本的讲法

### 30 秒

> Agent 的一次运行很长、带副作用，崩了以后很难回答"执行到哪、会不会重复扣款、怎么复现"。我用 Rust 做了一个单机持久化执行引擎：每一步写 journal，崩溃后重放恢复，已完成的活动复用结果，副作用用幂等键收敛。在同一条 journal 上，我异步构建了一个 HNSW 语义记忆索引，它可以落后、可以重建，永远不阻塞写入。我用崩溃矩阵和召回/延迟数据验证了这些不变量。

### 2 分钟

在 30 秒基础上补：

1. **拓扑**：工作流 → journal → 异步 indexer → HNSW；`memory.search` 是普通 activity。
2. **一致性**：日志是真相，索引最终一致，查询返回 watermark；checkpoint 原子写。
3. **一个数字**：比如"20 个崩溃点 × 100 次运行，违反次数 0"或"recall@10 0.96，p99 3ms"。
4. **一个边界**：单机、至少一次副作用、没做分布式。

### 10 分钟（白板）

顺序：为什么需要 → 拓扑图 → 一次正常 run 的事件序列 → 8 个崩溃点 → checkpoint/追平 → HNSW 召回/延迟 → 没做什么。

白板图用 `docs/ARCHITECTURE.md` 的第一张，重点标出"写路径不等索引"和"索引可重建"。

## 四、要产出的数据

**Engine**

- 崩溃矩阵：20 个崩溃点 × 100 次，违反 = 0
- 恢复时间 vs 日志大小
- 吞吐：每条 fsync vs group commit
- 重放 100 次状态哈希一致

**Memory**

- recall@10（HNSW vs 暴力）
- 查询 p99、QPS、内存
- 索引落后 p50/p99、追平时间
- 重复 episode = 0

**Integration**

- 写入到可检索延迟
- engine + indexer 组合崩溃的恢复结果

数字不好看也要如实写。真实数字比没有数字强。
